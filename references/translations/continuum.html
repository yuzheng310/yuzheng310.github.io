Continuum: Efficient and Robust Multi-Turn LLM Agent Scheduling with KV Cache Time-to-Live

基于 KV Cache 租约驻留（TTL）的高效鲁棒多轮智能体调度系统 —— 中文精读

作者：Hanchen Li, Runyuan He, Joseph Gonzalez, Ion Stoica 等（伯克利 Sky Computing 实验室） 基准场景：SWE-bench, Mini-SWE-agent, BFCL Function Calling

1. 摘要与核心立论（Abstract & Problem Statement）

在现代大语言模型服务系统中，KV Cache 的淘汰策略（Eviction Policy）是决定系统性能的命脉。 传统的推理引擎（如 vLLM、SGLang、TGI）都内嵌了一个默认假设：一旦一个请求的解码结束（生成完毕），它的 KV Cache 就不再紧急，可以直接驱逐（Evict）以腾出显存给新请求。 论文将这种传统策略正式命名为：“轮次结束驱逐制（End-of-Turn Eviction）”。

💥 致命缺陷：End-of-Turn Eviction 摧毁了 Agent 性能！

在普通人机聊天中，用户看屏幕、敲键盘需要十秒甚至几十秒，驱逐 KV Cache 影响不大。 但在以 软件工程智能体（SWE-bench / Devin）、电脑操作（Computer Use）和科研智能体 为代表的新型 Agent 负载中， 工作流是交替进行的：(1) 模型推理一步生成动作 $\rightarrow$ (2) 调用外部工具（如执行 bash 命令、git diff） $\rightarrow$ (3) 将工具结果作为新观察输入，立即开启下一步推理。
外部工具往往在 0.5 秒到 2 秒内 就会返回结果！ 如果系统在第 (1) 步结束时把它的 KV Cache 扔掉，当第 (3) 步在 1 秒后到来时，系统必须从头重新跑一遍长达几千上万字的历史 Prefill，或者从 CPU 重新搬运。

2. 传统推理引擎的两大失败模式（Failure Modes）

论文在第 1 章和第 2 章用极其生动的图示，揭露了现有大模型服务系统在面对 Agent 时必然遭遇的两大惨败模式：

图 1：以往 Agent 服务系统的两大失败模式（论文图 Figure 1）
红色方块代表系统设计缺陷引发的额外巨大开销。

① 失败模式 A（原始无状态 / 朴素 vLLM）：重复 Prefill 算力黑洞

模型吐出 bash: git diff 命令后，请求在系统内被当成已完成，KV Cache 当场被回收。 1 秒后工具返回，系统把前面 10 轮的几万字上下文重新送入 GPU。 这不仅导致 TTFT（首字延迟）暴涨，而且 GPU 的算力全在反复做毫无意义的矩阵乘法。

② 失败模式 B（即使支持了 CPU 卸载）：累积性每轮排队等待（Per-Turn Queueing Delay）

这是论文最具突破性的洞察！很多系统（如 InferCept、LMCache）以为“只要把 KV 存到 CPU 上再拉回来就万事大吉了”。 但论文证明：一旦你在轮次结束时把请求从 GPU 显存驱逐，灾难依然会发生！

  • 当工具执行完毕，该请求作为一个“新轮次”回到推理引擎时，哪怕可以从 CPU 恢复，它也必须重新在 WAITING 队列里老老实实排队，等待其他正在跑的请求把 GPU 显存腾出来！
  • 一个 Agent 任务通常有 10 到 30 个轮次，每一轮都在承受漫长的重新排队等待（Per-Turn Queueing Delay）！
  • 如图 2 所示，这个等待时间在每轮不断累加叠加，端到端任务完成时间（JCT）几乎和没有任何缓存的朴素 vLLM 一样惨烈！
图 2：CPU 卸载模式下的每轮累积排队延迟（论文图 Figure 4）
证明了单纯算重载成本是不够的，被驱逐出显存后重新排队（Waiting Time）在多轮中不断放大。

4. Continuum 系统设计：显式锁定（Pinning）与动态租约（TTL）

为彻底打破上述僵局，伯克利团队在 vLLM 之上设计了 Continuum 引擎：

图 5：Continuum 系统整体架构与工作流（论文图 Figure 5）
展示了工具调用解析器、基于租约的 Pin Request 机制、以及调度器协调逻辑。

系统核心机制

  1. 跨轮次程序标识符（program_id）：
    客户端在请求中携带 program_id，服务端引擎借此识别多轮 Agent 会话，将离散的 HTTP 请求串联为一个生命周期实体。
  2. 运行时按 TTL 显式保留工具调用期间的 KV 状态，在租约到期后允许回收。
  3. 动态租约倒计时（Time-to-Live, TTL）：
    系统并不是无限期死锁显存（防止工具卡死导致 OOM），而是为这个锁定设定一个倒计时 $\tau^*$。 如果工具在 $\tau^*$ 内返回，下一轮**直接以 0 排队、0 重算在 GPU 上满血恢复执行**；如果超时，系统才安全回收显存作为兜底。

5. TTL 核心数学模型：占显存排队的代价 vs 重算的代价

Continuum 最硬核的部分在于它建立了一个**数学成本效益分析模型**：

  • 收益（Benefit）：保留 KV 锁定时，如果工具在此期间返回，不仅省去了重算 Prefill / CPU 重新载入的开销 $T_{reload}$，还彻底消除了重新进队列的排队惩罚 $T_{queue}$；
  • 代价（Cost）：在这段时间里，显存被锁定，可能会让其他新进来的普通请求多等待一小段时间；
  • 最优决策：通过求解微积分极值，动态为每个工具计算出最优的租约时间 $\tau^*$，使全局任务的端到端完成时间（JCT）达到理论最小。

评测硬核数据总结：

  • 端到端完成耗时：在 SWE-bench 真实任务中，Continuum 相比传统无状态系统实现了 最高 8.18 倍的端到端延迟降低！
  • 系统吞吐量：在高并发工具调用下，吞吐量提升了 1.10x 到 3.22x；
  • 消融实验结论：显式锁定（Pinning）是整个提速的核心支柱，单纯靠无状态被动缓存，在真实工具调用面前会被彻底击穿。

7. 个人思考：与会话 KV 管理的联系

以下是阅读后的个人思考，不属于论文原文。

在 Qwen3 Runtime 中，我关注工具等待期间的会话状态保存、前缀校验与增量恢复。只有前缀匹配且缓存有效时，后续请求才能复用历史 KV；显存压力、回收策略和传输成本都会影响收益。

这与论文讨论的缓存生命周期问题有关，但实现范围和评测条件不同。Qwen3 Runtime 面向单 GPU 的 Agentic Rollout 推理层；论文中的集群架构、调度算法与性能结果不能直接视为该项目已实现或已验证的能力。
