Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

以 KVCache 为中心的大模型解耦式推理架构 —— 中文精读与图文全解

原作者：秦若愚、李哲铭、张明星、徐欣然等（Moonshot AI / 清华大学） 模型底座：Kimi 生产系统 / LLaMA2-70B 架构

1. 摘要与核心立论（Abstract）

Mooncake（月饼）是月之暗面为旗舰模型服务 Kimi 自研的大规模在线推理系统。 传统的大模型服务系统将 GPU 显存视作唯一的瓶颈，并将预填充（Prefill）与自回归生成（Decode）混部在同一次迭代中。 而 Mooncake 彻底推翻了这一假设，提出了“以 KVCache 为中心的解耦式架构”。

💡 论文的第一性原理思想

“用廉价的存储，换取宝贵的 GPU 算力”（Trading more storage for less computation）。
通过盘活 GPU 集群中过去完全闲置的 Host CPU 内存、DRAM 与 NVMe SSD，构建跨主机的全局分布式 KVCache 资源池， 确保多轮对话和长上下文交互中的历史状态能够被 100% 留存与复用，从而终结长文本场景下 GPU 算力反复自我重算的灾难。

① 悬殊的输入输出比（平均 40:1 的算力倒挂）

  • 平均 Prompt 输入长度：高达 7,590 tokens；
  • 平均 Output 生成长度：仅有 182 tokens；
  • 输入输出比：平均高达 40:1 甚至更高！

这意味着：用户每次在前端只看模型吐出一小段话，而 GPU 超过 95% 的矩阵乘法算力，全都被用来啃那几千上万字的历史输入！ 如果系统不把会话历史的 KV Cache 保存下来，下一次用户再问一句话，GPU 就要把这 7,590 个 Token 重新做一次巨大的 GEMM 运算。

揭示了缓存访问极度不均的“二八长尾效应”。

② 物理块热度的严重极化（二八定律与热点踩踏）

图 2 统计了以 512 tokens 为一个物理块的哈希复用率：

3. 物理特性的根本冲突：为什么 Prefill 与 Decode 必须物理隔离？

在传统架构（如早期 vLLM）中，Prefill 和 Decode 被混部在同一台机器的同一次 Forward 中。 Mooncake 论文深入测试并量化了两者的微架构冲突：

图 3：LLaMA2-70B 下 Prefill 与 Decode 阶段的归一化吞吐与延迟曲线（PDF Figure 2）
左图展示 Prefill 耗时随序列长度超线性增长；右图展示 Decode 耗时随 Batch 亚线性增长。
维度 预填充阶段 (Prefill) 自回归生成阶段 (Decode)
物理计算瓶颈 计算密集型（Compute-Bound），跑大矩阵乘法（GEMM） 访存密集型（Memory-Bound），受限于 HBM 显存带宽（GEMV）
延迟与长度关系 超线性（Superlinear）暴涨（随输入长度平方级增长） 亚线性（Sublinear）微涨（单步只生成 1 个 token）
核心业务 SLA 首字延迟 TTFT（Time to First Token） 字间生成延迟 TBT（Time Between Tokens，打字流畅度）
混部时的灾难 当长达 8k 的长 Prefill 冲入时，会强行夺走 GPU 所有 SM 算力数百毫秒；
正在打字的 Decode 请求被严重队头阻塞（Head-of-Line Blocking），TBT 暴增数十倍，打字机瞬间卡死。

4. Mooncake 全局解耦架构（System Architecture）

为解决上述矛盾，Mooncake 构建了一个彻底解耦的分布式多层系统：

图 4：Mooncake 分布式全景架构图（PDF Figure 1）
清晰展示了全局调度器 Conductor、解耦的 Prefill 池、Decode 池，以及贯穿全局的分布式 KVCache 存储池。

系统核心四大组件：

  1. 全局调度器（Conductor）：
    作为整个集群的大脑，不再仅仅按“请求数”做轮询，而是按全局 KVCache 的分布位置与命中长度来规划每一次分发。
  2. Prefill 计算集群：
    专门负责吃大算力。采用分块流水线并行（Chunked Pipeline Parallelism, CPP），以极高的 MFU 快速推进大输入， 算完后不留在本地 GPU 显存，立刻推走。
  3. Decode 生成集群：
    专门负责自回归打字。利用大容量聚合 HBM 与连续批处理（Continuous Batching），在平稳的 TBT 下跑满吞吐。
  4. 跨节点高速通信引擎（Messenger）：
    基于 GPUDirect RDMA 技术自研的高速传输服务。在 Prefill 计算逐层输出的同时，通过后台流水线将 KV Cache 异步流式灌入目标节点，将跨机传输开销完全隐藏（Overlap）。

5. 分布式 KVCache 存储池与分层流转（Storage & Workflow）

图 5：CPU 内存中基于双哈希链的分布式 Paged KVCache 排布（PDF Figure 3）
每个物理块（512 tokens）的哈希值同时由自身内容和前驱块的哈希值决定，杜绝前缀冲突。

如图 5 所示，Mooncake 将原本被浪费的 Host CPU 内存组织为一个巨大的逻辑缓存池：

  • 块级双哈希链（Block Dual-Hash）：每个 512-Token 块的键为 Hash = SHA256(Block_Tokens + Prev_Block_Hash)，保证了哪怕同一个句子出现在不同上下文中，也能精准区分其精确前缀。
  • 分层沉降：最热块驻留 GPU HBM，次热块进入 CPU DRAM，长尾冷块异步沉降至 NVMe SSD。
图 6：端到端单请求的四阶段执行流水线（PDF Figure 6）
展示了前缀复用、逐层增量 Prefill、RDMA 异步流式灌入、以及解码节点连续批处理。

四步执行流水线：

  1. KVCache 复用（Bootstrap）：根据调度决议，若存在历史前缀，直接通过 RDMA 从分布式存储池载入 GPU HBM；
  2. 分块增量计算（Incremental Prefill）：只对新增的 Uncached Tokens 进行计算；
  3. 逐层流式传输（Layer-wise Overlap Transfer）：模型每算完一层 Transformer Layer，Messenger 就通过 RDMA 把这层的 KV 实时推送出去，与后续计算完全并行重叠；
  4. 连续批处理解码（Continuous Decoding）：Decode 节点接纳完全部上下文后，加入连续批处理队列平稳吐字。

⚠️ 启发式热点迁移（Hot-Spot Migration）的妙处

如果某个长文档极其火爆，大家都涌向持有它的 Prefill 节点，该节点的排队时间 T_queue 会迅速膨胀。 当排队时间超过了“在另一台空闲卡上重算或远程传输”的代价时，调度器会主动把请求转派给备用节点，并在后台顺带完成多副本复制。 系统无需复杂的全局预测模型，纯靠局部启发式逻辑就自动消除了网络与算力热点！

在超长 Prompt（16k 到 128k）压力测试下： Mooncake 相对 vLLM 实现了 50% ~ 525% 的惊人吞吐提升！

8. 终极启示：对我们项目（Session KV / qwen3-runtime）的映射

读完整篇 Mooncake 论文，再回看我们自己的项目实现，所有设计完全能形成严密的逻辑闭环：

🎯 核心认知闭环
  1. 为什么单靠普通前缀缓存（APC）在多轮 Agent 下行不通？
    Mooncake 的生产数据证明了：在高并发和长上下文中，显存资源是极其短缺的。 APC 的引用计数为 0，属于随时可被回收的弱引用。在 Agent 暂停等待工具返回的 1~3 秒内，这些块极易被并发涌入的新请求覆盖写掉，导致缓存颠簸（Cache Thrashing），下一轮被迫退化回漫长的全量重算。
  2. 为什么我们的项目必须设计 PAUSED 状态与显式 Session KV？
    正是为了在单机多轮 Rollout 场景下，建立有状态的生命周期契约（Leased Contract）： 在等待外部工具期间，既让出调度槽位（不占 max_num_seqs 算力），又锁定其物理块（或卸载到 CPU 内存）， 100% 确定性地杜绝了已知历史的二次 Prefill！
  3. 架构高度的一致性：
    Mooncake 是在超大规模 GPU 集群上通过 RDMA 和分布式内存池做全局 Session KV；
    我们的 qwen3-runtime 是在单机多轮 Agentic RL 上通过 hold_kv、PAUSED 和分层 CPU Offload 做本地 Session KV。
    两者的底层第一性原理完全相同：算力极其昂贵，存储相对便宜；决不能把时间浪费在重复计算已知历史上！
